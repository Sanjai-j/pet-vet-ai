# Pet Vet AI — API reference

Base URL: `/api`. JSON in, JSON out. Errors use
`{ "error": { "code": string, "message": string, "details": unknown } }`.

Authentication: `Authorization: Bearer <jwt>`. Roles: `owner`, `vet`, `admin`.

Interactive discovery: `GET /api/health` and `GET /api/config/public` need no token. A full
OpenAPI document is not generated by this build; this file is the contract.

## Pet Vet AI

| Method | Path | Role | Notes |
| --- | --- | --- | --- |
| GET | `/ai/status` | any | Provider mode, configured model, daily cap, disclaimer |
| POST | `/ai/chat` | owner, admin | `{ petId, message, conversationId? }` → `{ conversationId, reply }`; daily cap; emergency-first. `reply.urgency` is one of `routine`, `prompt`, `urgent`, `emergency`. A model answer that breaks a safety rule (dose, prescription, stated diagnosis, home remedy, claimed examination, missing referral) is discarded and replaced by the deterministic answer, which reports `mode: "deterministic"` and says why in `modeReason` |
| GET | `/ai/conversations?petId=` | owner | Conversation list |
| GET | `/ai/conversations/:id` | owner, admin | Messages with citations, emergency flag, capability status |
| DELETE | `/ai/conversations/:id` | owner, admin | Delete a conversation |

`reply` shape: `{ answer, citations[], emergency: {ruleId,label,advice}|null, capability:
{task,taskLabel,status,evidenceSummary}, mode: 'deterministic'|'llm'|'blocked', modeReason,
needsClarification?, urgency, followUps?, llmAttempted, providerError?, disclaimer, referral }`.

`modeReason` is one of `llm_answer`, `no_model_configured`, `model_disabled_by_admin`,
`provider_error`, `guard_rejected`, `emergency`, `emergency_llm`, `emergency_provider_error`,
`emergency_guard_rejected`, `ai_disabled`, `medication_blocked` or `profile_mismatch`. It
answers "why did this answer not come from the model?" without reading server logs, which was
previously impossible from the client. `llmAttempted` says whether the provider was called at
all, and `providerError` carries the provider's own failure text (truncated, never a key or
token) when the call failed.

`citations[]` contains only the numbered approved sources the answer actually referenced. A
reply built from general model knowledge carries no citations rather than being dressed up
with unrelated approved rows.

A red flag (`emergency`) is a two-layer reply. The deterministic safety instruction is composed
first from the matched rule and is always the first text in `answer`; approved references are
attached only when their own title/category is about that red flag (`emergencyReferenceTopic`),
so "not eating for days" no longer arrives with vomiting and diabetes cards. With a model
configured and permitted, the model is then asked for a supplementary explanation, returned in
the same answer above the optional `followUps` questions. Text that softens the red flag
(waiting, home monitoring, reassurance, a routine appointment, a diagnosis, a medicine or dose)
is discarded by `checkEmergencyAnswer`, leaving the deterministic instruction with `modeReason:
"emergency_guard_rejected"`; a timeout or provider error does the same with
`"emergency_provider_error"`. A red flag is checked before every other rule, including the
profile check and the medication refusal.

Each non-emergency answer is assembled in this order: admin off switch →
medication refusal → selected-pet check (`services/profile-match.ts`: species, breed, age and
weight in the question are compared with the selected pet; a mismatch returns a clarification
with `needsClarification: true` and calculates nothing) → the pet's own record
(`services/pet-context.ts`: profile, conditions, vaccination records and checkpoints, today's
care plan, weight log, appointments) → approved reference retrieval (knowledge chunks,
approved nutrition rows, approved vaccination schedule rows) → LLM when configured, otherwise
a deterministic composer. Feeding questions additionally get a computed plan
(`services/feeding-plan.ts`, same numbers as `GET /pets/:petId/feeding-plan`). The model is
invoked whether or not a reference matched — retrieval restricts what it may cite, it does not
decide whether it may answer. Record facts are used for dates, weights and history; clinical
claims still require an approved source, and a medication question is refused regardless of
what the record contains. Record-only questions are answered from the record with no citation
and an explicit "not a diagnosis" line.

## Food & nutrition knowledge

The starter workbook (`Pet_Vet_AI_Food_Nutrition_Starter_Dataset.xlsx`, and the expanded
breed dataset) is imported into six normalized tables — `nutrition_guidance` (suitable foods
+ foods to avoid per species/life stage/goal), `nutrition_hazards`, `nutrition_recipes`,
`nutrition_breed_guidance`, `nutrition_health_rules`, `nutrition_sources` — via
`npm run import:workbook`. Every row is validated on import (required columns, species codes,
life stages, URLs), starts as `review_status = 'pending'`, and keeps its source URL and
species mapping. Unreviewed rows never reach owners or the RAG mirror
(`knowledge_chunks` rows tagged `nutrition_record_id`, synced only on approval).

| Method | Path | Role | Notes |
| --- | --- | --- | --- |
| GET | `/pets/:petId/nutrition` | owner, shared vet, admin | Personalized profile filtered by species, life stage, allergies, conditions and veterinary dietary restrictions. `missingInfo[]` lists what is not recorded (guidance is withheld, not guessed). Recipes carry `completeDietWarning` unless nutritional adequacy was professionally validated; cow/goat get a `feedPlanRequired` notice instead of quantities; unknown safety is reported as unknown |
| GET | `/pets/:petId/feeding-plan` | owner, shared vet, admin | Deterministic plan from this pet's own data: life stage from age, approved breed guidance, condition rules matched against what the owner recorded, allergy cross-check against recipe ingredients. `energy` is `null` for birds (and with an `energyUnavailableReason`) because the equations are validated for dogs and cats; for dogs and cats it returns a maintenance **range** with its formula and assumptions, never a single prescribed intake. `missingInfo[]` names what to record next |
| GET | `/nutrition/hazards?species=&q=` | any authenticated | Approved hazard records only; the note states that “not listed” never means safe |
| GET | `/admin/nutrition/queue` | admin | Pending/approved/rejected counts per record kind |
| GET | `/admin/nutrition/:kind?status=&limit=` | admin | `kind ∈ guidance\|hazard\|recipe\|breed\|health_rule\|source`; `status ∈ pending\|approved\|rejected\|all` |
| PATCH | `/admin/nutrition/:kind/:id` | admin | Edit allowed fields. Editing an approved record returns it to `pending` so owners never see unreviewed edits |
| POST | `/admin/nutrition/:kind/:id/review` | admin | `approved`, `rejected` or `pending` (reopen) with optional notes; syncs the RAG mirror and audits |
| GET | `/admin/nutrition/:kind/:id/versions` | admin | Version history with actor, action, notes and full row snapshots |

## WebSocket protocol

Connect to `/ws?token=<jwt>`, or to `/socket?token=<jwt>` — the same handler. The Angular client uses `/socket` because Cloudflare Pages reserves `/ws` for the platform when the app is hosted there; see [DEPLOY_FREE.md](DEPLOY_FREE.md). Frames are JSON; unknown types return `{ type: "error", message }`.

Client → server

```jsonc
{ "type": "ping" }
{ "type": "chat",    "threadId": "...", "body": "...", "fileId": "..." }
{ "type": "typing",  "threadId": "..." }
{ "type": "read",    "threadId": "..." }
{ "type": "webrtc",  "appointmentId": "...",
  "signal": { "kind": "join" | "offer" | "answer" | "candidate" | "leave", "sdp": "...", "candidate": {...} } }
```

Server → client

```jsonc
{ "type": "ready",        "userId": "..." }
{ "type": "message",      "message": { "id", "threadId", "senderId", "senderName", "body", "fileId", "createdAt" } }
{ "type": "notification", "notification": { "id", "title", "body", "kind", "link", "createdAt" } }
{ "type": "typing",       "threadId": "...", "userId": "..." }
{ "type": "webrtc",       "appointmentId": "...", "fromUserId": "...", "signal": { ... } }
{ "type": "error",        "message": "..." }
```

`chat` frames are persisted before broadcast, so the sender also receives the canonical message
(with id and timestamp). Every frame re-checks that the caller belongs to the thread or to the
appointment, and video signalling additionally requires `status = 'accepted'`.
